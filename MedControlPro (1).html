Análisis de Seguridad — Por qué el Patrón Estado supera a if/else
✗ Estructura if/else — Riesgos críticos
function handleAirAlarm(currentState) {
  if (currentState === "infusion") {
    stopInfusion();
    triggerAlert();         // ✓ Cubierto
  } else if (currentState === "pausa") {
    // ← OMISIÓN SILENCIOSA:
    //   El desarrollador olvidó este caso.
    //   En estado Pausa, la alarma de aire
    //   NO se activa. ERROR CRÍTICO DE SEGURIDAD.
  }
  // Completado, Config → sin manejo → BUG
}
// Añadir un nuevo estado = revisar todos
// los if/else en todo el código. O(n²).
Riesgos: estados no manejados silenciosos, condiciones de carrera, deuda técnica O(n²), imposible auditar cobertura.
✓ Patrón Estado — Seguridad estructural
class IVPausaState extends IVState {
  // La clase SABE manejar la alarma
  // independientemente desde dónde venga.
  airAlarm() {
    this.ctx.setState(             // ✓ Atómico
      new IVAlertaState(this.ctx)  // ✓ Siempre correcto
    );
  }
}

class IVInfusionState extends IVState {
  airAlarm() {                     // ✓ Mismo contrato
    this.ctx.setState(
      new IVAlertaState(this.ctx)
    );
  }
  // Nuevo estado = nueva clase aislada. O(1).
}
Ventajas: transiciones atómicas (exit→enter), cobertura garantizada por estructura, escala O(n), fácil de auditar.
ENCAPSULAMIENTO
Cada estado gestiona solo su lógica. Modificar AlertaState no afecta ningún otro estado del sistema.
TRANSICIONES ATÓMICAS
exit() siempre se ejecuta antes de enter(). Nunca existen estados intermedios inválidos ni condiciones de carrera.
ALERTAS CONCURRENTES
La alarma de aire actúa como interrupción de máxima prioridad. El patrón garantiza que desde cualquier estado la transición a Alerta es siempre correcta.
